# Identity: scope boundaries, sessions, and permissions

The changes require the additive EF migration `20261122000100_AddAuditScope` before starting the updated API. It adds audit `ScopeId` and three fields for safe refresh retries. Historical audit events remain available at tenant scope; their organization/branch is intentionally not guessed.

From the repository root, with the target database configured for Identity.Api:

```powershell
dotnet ef database update --project src/Services/Identity/Identity.Persistence --startup-project src/Services/Identity/Identity.Api
```

Stop/restart the existing Identity.Api dev process when rebuilding its usual output directory; a running process locks its DLLs. Tests can build to the independent directory below without stopping it. The regression runner also generates `.artifacts/identity-session-update.sql` without connecting to a database, for review or manual application.

## Session behavior

- `LoginSessions__MaxConcurrentSessions` sets the limit (default **5**, valid range 1–100). A new successful login revokes the least recently active sessions when necessary. Failed logins never evict sessions.
- Login limits are serialized per account on SQL Server, avoiding simultaneous login range-lock upgrades.
- Refresh rotation uses the session row version. For **10 seconds**, the immediately previous credential can retrieve the same successor rather than create a competing rotation. The successor is stored only as a Data Protection ciphertext; current/previous credentials are compared using hashes. Revoked and expired sessions cannot use this retry window.
- All API instances must share their Data Protection key ring. Set `DataProtection__KeyRingPath` to a protected shared persistent directory when deploying multiple instances, and use the same `DataProtection__ApplicationName` across instances. Existing installations should preserve their application discriminator to keep previously issued email/reset tokens valid; leaving this setting unset preserves ASP.NET's current default.
- Logout uses an existing access token or a refresh credential, without rotating first. Session revocation uses an atomic database update so a concurrent refresh cannot restore the session. Local cookies are cleared even if the API is unavailable; that failure is reported rather than presented as confirmed server revocation.
- The Next.js proxy coalesces parallel refreshes, preserves the decrypted email, and buffers mutation bodies before retrying a 401. Transient upstream errors preserve session cookies. Requests have timeouts; each logout attempt is bounded to three seconds.
- Activity and the latest IP are updated on authenticated requests, at most once per minute unless the IP changes.

## Trusted client IPs

User-Agent is forwarded for display only; it is never an authentication factor or a device identifier. Session IDs are generated by the API.

For a deployment behind a trusted ingress:

1. Configure the ingress to **overwrite**, not append untrusted client values in, `X-Forwarded-For`.
2. Set FE `IDENTITY_TRUST_PROXY_HEADERS=true` only behind that ingress.
3. Set BE `TrustedProxies__0`, `TrustedProxies__1`, etc. to the actual immediate FE proxy IPs.

Without this configuration, the API deliberately uses its observed network peer instead of trusting a supplied IP header. A direct local FE/BE installation normally observes loopback. Do not enable IP forwarding on an unprotected internet-facing Next.js server.

## Data and permission boundaries

- Tenant scope can list all accounts within the tenant.
- Organization scope lists accounts explicitly assigned there or in its branches.
- Branch scope lists accounts explicitly assigned to that branch. Tenant-wide accounts do not become editable branch members implicitly.
- Individual user routes verify membership, including session inspection/revocation. Account-wide status, profile, custom claims, and role-definition mutations require tenant scope. Role assignments and role permissions can be managed in their selected scope.
- A scoped account creation needs an initial role to establish membership. Granting initial roles requires `Identity.Users.Assign` in addition to `Identity.Users.Create`.
- Audit queries enforce the selected scope; only platform administrators can inspect failures with no attributable tenant. Failed security mutations are recorded without request bodies or credentials.
- `/permissions` is the separate permission matrix page. It selects a role, searches resources, edits binary grants, tracks unsaved changes, and saves against the current tenant/scope. The role page links to it.
- Member rows expose device/session inspection to users with `Identity.Sessions.View`, and revocation requires `Identity.Sessions.Revoke`. Login history additionally requires `Identity.Security.View`.
